# Alumni System Audit — 2026-09-07

## Scope and result

This review covered the React alumni site, the admin portal, Express API routes, Supabase access patterns and RLS schema, storage uploads, authentication controls, and production dependencies.

The production build and all eight server/security tests pass. `npm audit --omit=dev` reports zero known production dependency vulnerabilities. Static checks found no committed environment file or client-side service-role key.

Live integration testing found one deployment blocker: the local `SUPABASE_SERVICE_ROLE_KEY`/secret credential returns HTTP 401 from the configured Supabase project. The publishable key succeeds against the same project. Replace the server secret with a current secret/service-role key from that project, restart the server, and check `GET /api/ready` before testing database-backed pages.

## Fixed in this pass

### Critical and high priority

- Closed a staff privilege-escalation path. Staff with member access can no longer promote accounts or suspend, deactivate, lock, reset, confirm, or revoke sessions for privileged staff/admin targets.
- Removed a shadowed duplicate member-edit route. Full member edits now reach the validated route, and role changes stay synchronized with `profile_roles`.
- Corrected scope ownership for generic resources. Events require Events access, jobs require Opportunities, news requires Moderation, reports require Analytics, and surveys require Settings.
- Prevented public event payload leakage. `/api/events` now returns an explicit field allowlist instead of spreading arbitrary admin JSON into the response.
- Added strict server validation for event title, description, status, schedule, deadline, capacity, coordinates, location, and image URL.
- Protected moderation from allowing non-super-admin staff to suspend a privileged account through one of its posts or comments.

### Functional connections and reliability

- Connected the home-page event preview. `/api/home` now returns the published event array that the client was already expecting.
- Aligned legacy event statuses (`active`, `approved`, and status-less records) with the published workflow. The schema migration normalizes these statuses for RLS and registration.
- Connected event capacity, registration deadline, visibility, and featured state to the admin editor.
- Enforced event registration deadlines in both the client and the database RPC. Existing registrants can still cancel after registration closes.
- Added a readiness endpoint (`/api/ready`) that distinguishes a running Node process from a working database credential.
- Made the public gallery resilient to a missing storage object; one broken image no longer takes down the whole gallery response.
- Connected the admin CAPTCHA setting to alumni login, registration, password recovery, and admin login. Configuration loading fails closed.

### Upload and input safety

- Gallery and event image uploads now reject unsupported MIME types and files larger than the storage limit before uploading.
- Event filenames now use collision-resistant UUIDs and explicit content types.
- Event check-in tokens are format-validated and rate-limited.
- Reminder sending, role changes, permission changes, email confirmation, password reset, session revocation, and account restrictions use the sensitive-operation limiter.
- Malformed permission-scope and role payloads now return 400 instead of becoming server errors.

## Existing controls that are working

- Helmet security headers, disabled Express fingerprinting, origin allowlisting, body limits, and API rate limits.
- Supabase token verification for admin APIs, verified admin/staff status checks, session-age enforcement, optional AAL2/MFA enforcement, scoped staff permissions, and protected audit logs.
- RLS-backed verified-member write boundaries for posts, comments, reactions, messaging, events, opportunities, reports, and gallery submissions.
- Private verification and gallery storage, owner-prefixed upload policies, signed URLs, community block enforcement, event-capacity locking, moderation state restrictions, and database-side abuse throttles.
- Privacy-safe directory/profile RPCs that avoid exposing alumni email addresses to other members.

## Remaining recommendations

### Deploy before release

1. Rotate the rejected Supabase server secret, keep it only in the server host, restart, and require `/api/ready` to return 200 in deployment health checks.
2. Apply the updated `supabase/schema.sql` once. Do not run concurrent schema jobs. The advisory transaction lock prevents overlapping executions, but production should move to immutable, numbered migrations rather than repeatedly executing one large schema file.
3. Ensure `CLIENT_ORIGIN` contains only the real HTTPS alumni/admin origins. Keep the service secret out of all `VITE_*` variables and rotate it immediately if it has ever been copied to a browser build or repository.
4. Keep CAPTCHA enabled in both this app and the Supabase Auth dashboard. The application setting and Supabase provider setting must be changed together.
5. Require admin MFA after every admin/staff operator has enrolled and verified a TOTP factor; otherwise enabling enforcement can lock operators out.

### Next engineering iteration

1. Replace `window.prompt` moderation, suspension, role, and deactivation flows with accessible confirmation dialogs that show the target, consequence, reason, and final confirmation.
2. Add Playwright end-to-end tests for admin event publish → alumni Events/Home visibility, profile edits, feed ownership menus, gallery submission/review, staff scope denials, and event registration/deadline/capacity behavior.
3. Move multi-step member role/profile/auth updates into transactional database functions or a compensating workflow so a network failure cannot leave `profiles`, `profile_roles`, and Supabase Auth temporarily inconsistent.
4. Add malware scanning for verification documents and chat attachments, image re-encoding/EXIF stripping, moderation queues for suspicious uploads, and scheduled deletion that enforces the configured retention periods.
5. Add structured logs and alerts for repeated 401/403/429/5xx responses, failed storage signing, failed cleanup, unusual admin actions, and readiness failures. Avoid storing sensitive document data in logs.
6. Add keyboard focus trapping/restoration and consistent Escape handling for every modal; audit contrast, button names, error focus, and mobile layouts with automated accessibility checks plus keyboard testing.
7. Code-split the main client bundle. The current production build reports a roughly 513 kB main JavaScript chunk, which can slow first load on mobile connections.
8. Add database integration tests in a separate test Supabase project. The current server suite validates API boundaries and schema text but does not execute the SQL migration or RLS policies against PostgreSQL.
